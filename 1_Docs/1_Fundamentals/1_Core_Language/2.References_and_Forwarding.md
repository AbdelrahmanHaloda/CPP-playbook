# References, Forwarding References, and std::forward

This document explains how C++ references interact with template deduction and value categories, and how forwarding references plus `std::forward` preserve correctness across function boundaries.

---

# 1. lvalue reference vs rvalue reference

## lvalue reference

```cpp
int a = 5;
int& ref = a;
```

- binds to lvalues only

---

## rvalue reference

```cpp
int&& ref = 5;
```

- binds to rvalues

---

## Important Reminder

```cpp
int&& x = 5;
x;  // lvalue ❗
```

> Named variables are always lvalues

---

# 2. Forwarding References

A **forwarding reference** is a parameter of the form `T&&` where **`T` is deduced** by the compiler.

```cpp
template<typename T>
void f(T&& x);   // forwarding reference (T is deduced)
```

It is **not** a forwarding reference in these cases:

```cpp
void f(int&& x);              // NOT forwarding (type is fixed)
template<typename T>
void f(const T&& x);          // NOT forwarding (cv-qualifier on T&&)
```

It also appears with `auto`:

```cpp
auto&& x = expr;  // forwarding reference (auto is deduced)
```

### Key condition

> T&& is not always forwarding reference — only when T is deduced (template or `auto`).

---

## Usage

A forwarding reference is used when a template function needs to:

- accept both lvalues and rvalues
- preserve how the argument was passed
- forward the argument to another function without breaking correctness

Example goal:

```cpp
void consume(int& x)  { /* lvalue path */ }
void consume(int&& x) { /* rvalue path */ }


template<typename T>
void wrapper(T&& x) {
    consume(std::forward<T>(x));
}
```

Here `wrapper` should work correctly for both:

```cpp
int a = 5;
wrapper(a); // should call lvalue version
wrapper(5); // should call rvalue version
```

---

## Why not just use `int&`?

```cpp
void wrapper(int& x);
```

This accepts lvalues only.
It cannot accept rvalues like:

```cpp
wrapper(5); // invalid
```

---

## Why not just use `int&&`?

```cpp
void wrapper(int&& x);
```

This accepts rvalues only.
It cannot accept lvalues like:

```cpp
int a = 5;
wrapper(a); // invalid
```

**Important:** `int&&` here is an **ordinary rvalue reference**, not a forwarding reference, because the type is already fixed and not deduced.

---

## Why Forwarding References Are Special

```cpp
template<typename T>
void wrapper(T&& x);
```

This can accept both:
- lvalues
- rvalues

But more importantly:

> it preserves the original value category of the argument

That is the core idea, achieved through template deduction together with the reference collapsing rules explained below.

---

## Why preserving value category matters

Because correctness would break if lvalues were treated like rvalues.

Suppose we pass an lvalue:

```cpp
int a = 5;
wrapper(a);
```

If the language deduced:

```cpp
T = int
x = int&&
```

then the function would treat an lvalue as movable rvalue.
That would be wrong.

It could:
- move from objects that should not be moved from
- call wrong overloads
- break caller expectations

So C++ preserves correctness by deducing differently (the mechanism behind this is explained below in reference collapsing).

---

## The key facts

When `T&&` is a forwarding reference:

- if argument is lvalue → deduce `T` as lvalue reference
- if argument is rvalue → deduce `T` as non-reference type

This gives:

- lvalue argument → final parameter becomes lvalue reference
- rvalue argument → final parameter becomes rvalue reference

In short:

> lvalue stays lvalue
> rvalue stays rvalue

---

## Example 1: lvalue argument

```cpp
template<typename T>
void f(T&& x);

int a = 5;
f(a);
```

Since `a` is an lvalue, deduction becomes:

```cpp
T = int&
```

Then:

```cpp
T&& → int& &&
```

After reference collapsing:

```cpp
int& && → int&
```

So the final parameter type is:

```cpp
int&
```

---

## Example 2: rvalue argument

```cpp
f(5);
```

Since `5` is an rvalue, deduction becomes:

```cpp
T = int
```

Then:

```cpp
T&& → int&&
```

So the final parameter type is:

```cpp
int&&
```

---

## One-line summary before reference collapsing

> `T&&` is used in templates so one function can accept both lvalues and rvalues while preserving correctness by keeping lvalues as lvalues and rvalues as rvalues.

# 3. Reference Collapsing (WHY THE ABOVE WORKS)

When references combine, they **collapse**.

## What does “reference collapsing” mean?

Reference collapsing answers this question:

> “If I end up with a reference to a reference (like `int& &` or `int& &&`), what is the final valid type?”

This happens mainly in **templates**, when types are deduced.

Example:

```cpp
template<typename T>
void f(T&& x);

int a = 5;
f(a);
```

- `a` is an lvalue
- So: `T = int&`
- Substitute into `T&&`:

```
T&& → int& &&
```

Now we must **collapse** `int& &&` into a valid type.

---

## Intuition (IMPORTANT)

> If there is ANY lvalue reference (`&`) → result is lvalue reference
> Only `&& &&` stays `&&`

This means:
- lvalue reference is “stronger”
- it dominates when mixed with rvalue reference

---

## Why this exists

Because types like this are illegal in C++:

```cpp
int& &;
int& &&;
int&& &;
```

So the language defines rules to reduce them into a single valid reference type.

---

## Formal Rules

```
T&  &  → T&
T&  && → T&
T&& &  → T&
T&& && → T&&
```

Read the table like this:

- `T& &` means: start with an lvalue reference, then add another lvalue reference
- `T& &&` means: start with an lvalue reference, then add an rvalue reference
- `T&& &` means: start with an rvalue reference, then add an lvalue reference
- `T&& &&` means: start with an rvalue reference, then add another rvalue reference

The result on the right is the final valid reference type after collapsing.

---

## Simplified Rule

> If there is ANY lvalue reference → result is lvalue reference

---

## Example

```cpp
template<typename T>
void f(T&);
```

If T = int&:

```
T& → int& & → int&
```

---

# 5. std::forward and Why It Is Needed

## The Problem

```cpp
template<typename T>
void wrapper(T&& x) {
    foo(x); // ❌ always lvalue
}
```

Why?

> x is named → lvalue

So even if the caller passed an rvalue, the named parameter `x` is still an lvalue expression inside the function body. Without `std::forward`, that original rvalue-ness is lost.

---

## The Solution

```cpp
template<typename T>
void wrapper(T&& x) {
    foo(std::forward<T>(x));
}
```

---

## What std::forward does

- if original was lvalue → keep lvalue
- if original was rvalue → keep rvalue

---

## Mental Model

```cpp
static_cast<T&&>(x)
```

That cast works together with deduction and reference collapsing to restore the original category that the caller provided.

---

# 6. End-to-End Example

```cpp
void foo(int& x)  { /* lvalue version */ }
void foo(int&& x) { /* rvalue version */ }


template<typename T>
void wrapper(T&& x) {
    foo(std::forward<T>(x));
}
```

---

## Case 1

```cpp
int a = 5;
wrapper(a);
```

- T = int&
- forward → int&
- calls: foo(int&)

---

## Case 2

```cpp
wrapper(5);
```

- T = int
- forward → int&&
- calls: foo(int&&)

---

# 7. Common Pitfalls

---

## ❌ Mistake 1: T&& is always rvalue reference

Wrong.

```cpp
template<typename T>
void f(T&& x);
```

Depends on deduction.

---

## ❌ Mistake 2: forgetting std::forward

```cpp
foo(x);  // always lvalue ❗
```

---

## ❌ Mistake 3: using std::move instead of forward

```cpp
foo(std::move(x)); // ❌ breaks lvalues
```

---

## ❌ Mistake 4: not understanding reference collapsing

Leads to wrong mental model of templates.

---

---

## Rule 3

---

# 10. How to Reason About It

---

### Step 1

> Is this `T&&` in a context where `T` is deduced?

---

### Step 2

> If yes, treat it as a forwarding reference

---

### Step 3

> Apply deduction and then reference collapsing

---

### Step 4

> Use `std::forward<T>(x)` when forwarding onward

# 11. Summary

> Forwarding references let one template accept both lvalues and rvalues, and `std::forward` preserves the caller's original value category when passing the argument onward.
